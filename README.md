# TenantAuth

A self-hosted, multi-tenant identity provider for small SaaS products: a lean alternative to Auth0 or Keycloak, built on .NET 10, Aspire and OpenIddict.

> Work in progress. Milestone 1, step 1: the Aspire skeleton with PostgreSQL and Redis.

## Project structure

```
src/
  AppHost/            Aspire orchestration (the entry point for local runs)
  ServiceDefaults/    Health checks, OpenTelemetry, resilience, service discovery
  Identity/           OpenIddict server + admin panel
  Api/                Protected resource server, validates access tokens
  Web/                Demo client application, runs behind a BFF
  Shared/             Shared contracts and constants
```

## Running locally

Prerequisites:

- [.NET 10 SDK](https://dotnet.microsoft.com/download)
- Docker (PostgreSQL and Redis run as containers)
- [Aspire CLI](https://get.aspire.dev) (the AppHost uses the CLI bundle for the dashboard and orchestrator)

```bash
dotnet run --project src/AppHost
```

The Aspire dashboard URL is printed to the console. It shows the `postgres`, `cache`, `identity`, `api` and `web` resources.

## Why: architecture decisions

### PostgreSQL and Redis run as containers, not managed Azure services

The AppHost uses `AddPostgres` and `AddRedis`. Aspire models these as container resources, and `azd up` deploys them as containers inside Azure Container Apps, which fits the free monthly grant. `AddAzureRedis` or `AddAzurePostgresFlexibleServer` would provision managed services that bill monthly (Azure Cache for Redis has no free tier). The application code is identical either way: same connection string, same client libraries. The trade-off is listed under known limitations below.

### Only Identity and Web get public endpoints

`identity` must be reachable by the browser (login pages, OIDC endpoints) and `web` is the user-facing app. `api` is only called server-side by the Web BFF, so it has no external endpoint. Less exposed surface, and it mirrors the BFF pattern: the browser never talks to the API directly.

### Resource wiring in the AppHost

- `identity` references the `identitydb` database and Redis (shared Data Protection keys).
- `web` references Redis because its authentication tickets will live there, so a session survives a restart and works across instances.
- `WaitFor` makes a service start only after its dependencies are healthy, which avoids startup races against a database that is still booting.
- The Postgres and Redis passwords are generated by Aspire and stored in the AppHost's user secrets, never in `appsettings.json`.

### One place for build settings and package versions

- `Directory.Build.props` sets `net10.0`, nullable reference types, implicit usings and `TreatWarningsAsErrors` for every project, so no project can silently opt out.
- `Directory.Packages.props` (Central Package Management) holds every NuGet version in one file. Upgrades are one-line changes and projects can't drift to different versions of the same package.

### Start minimal, add frameworks when a step needs them

Identity, Api and Web start as empty ASP.NET Core apps with only service defaults and health endpoints. Blazor Server, OpenIddict and EF Core are added in the steps that use them, so every dependency in the repo has a reason to be there.

## Known limitations

- Redis and PostgreSQL run as containers; a production deployment would use managed services with backup and high availability.
- Postgres has no data volume yet, so local data is recreated on every run.
